## Major empirical findings (durable knowledge in `docs/ENCODER_NOTES.md`)

1. **zlib HUFFMAN_ONLY is a full 3-way decision** (FIXED / DYNAMIC / STORED),
   not 2-way. My initial model was wrong; the probe corrected it.
2. **zlib's `stored_len + 4 <= opt_lenb` formula underestimates stored by
   one byte** — omits the BTYPE+padding header. Net: zlib picks STORED
   when it's actually 1 byte larger than fixed. Required to reproduce.
3. **NIL=0 sentinel makes position 0 unmatchable.** Hash chains use 0 as
   the end-of-chain sentinel; the match-attempt check `if (hash_head != NIL)`
   therefore rejects position 0 as a match source. This causes "AAAA" to
   emit 4 literals instead of a match.
4. **Level doesn't matter for HUFFMAN_ONLY across L1-L9.** Skips matches
   entirely; only Huffman tree-building changes, and that's frequency-driven.
5. **memLevel doesn't matter for HUFFMAN_ONLY on small inputs** (would
   matter at multi-block boundaries — see probe #12).
6. **L1 ≡ L6 ≡ L9 for many real-world inputs.** Easy matches converge
   across chain depths and lazy thresholds. Detector returns first
   registered match (`#3`).
7. **HUFFMAN_ONLY-STORED ≡ level=0 byte-for-byte** when both pick STORED
   for the same input (level=0 always emits stored; HUFFMAN_ONLY emits
   stored when its cost model picks it). #1 attributes correctly.
8. **gzip wrapper OS byte is platform-dependent.** We see `0x13` on Darwin
   nixpkgs; not in RFC 1952's table. Likely needs per-OS gzip fingerprint
   entries or a wildcard.
9. **gzip XFL byte depends on strategy, not just level.** HUFFMAN_ONLY
   → XFL=4 regardless of level. Probe #13 pending for full characterization.

## Major correctness bugs found + fixed during implementation

1. **`longestMatch` returned only length, not position.** Callers used
   `hash_head` (chain head) as match position, which is wrong when a
   deeper chain entry holds the longest match. Tests passed for L1 because
   our test inputs had ≤1 chain entry; broke for level 6+ on longish input.
2. **`best_len` not initialized to `prev_length`.** zlib's optimization
   skips matches shorter than the previous one. Without it, we'd find
   shorter matches zlib wouldn't (and our "found a shorter match" logic
   would diverge).
3. **Chain length not halved when `prev_length >= good_match`.** zlib's
   speed/quality tradeoff. Without it, we walk deeper than zlib and find
   matches zlib wouldn't, diverging the output.
4. **L1's `max_lazy_match` was 0 (should be 4).** zlib's `deflate_fast`
   uses this field as `max_insert_length`: when match_length ≤ this,
   insert intermediate positions into the hash chain. Without it, short
   matches (3-4 bytes) leave gaps in our hash chain — diverging from
   zlib on inputs with many short matches (common in English text).

## Known gaps before v0.1 ship

1. **DEFAULT_STRATEGY corpus divergence.** Some bug remaining; manifests
   only on non-trivial real inputs. Corpus hit rate is 35% across all
   configs (75% for covered configs). Hand-debugging needed — compare
   our output vs zlib's byte-by-byte for a specific small failing
   input, find the first divergence, fix.
2. **Multi-block boundary heuristic.** Inputs > ~16KB (lit_bufsize at
   memLevel=8). zlib's algorithm: accumulate symbols until
   `lit_bufsize-1`, emit block, repeat. Every 8192 symbols re-evaluate
   compression ratio and force-flush if poor. The simpler "always at
   lit_bufsize" version probably covers 95%+ of cases.
3. **Strategy fingerprints.** RLE / FIXED / FILTERED not yet registered.
   RLE = LZ77 but distance must be 1. FIXED = forced BTYPE=01 in the
   dispatch. FILTERED = LZ77 but matches with distance > threshold for
   certain inputs filtered out.
4. **gzip wrapper handling.** Header (variable) + 4-byte CRC32 + 4-byte
   ISIZE trailer. Probe #13 first for XFL/OS sensitivity.
5. **zlib wrapper handling.** 2-byte CMF+FLG header + 4-byte adler32
   trailer. Simpler than gzip.
6. **Real-world corpus harvest.** Current "corpus" is project source
   files — meaningful but synthetic. v0.1 goal wants 1000+ real-world
   `.docx`/`.epub`/`.zip` files.

## Architectural decisions made + why

1. **One Zig core; no runtime zlib dependency.** Library and CLI never
   link libz. Test-time only.
2. **Inline registry as a `pub const FINGERPRINTS` array, not a separate
   `registry.zig` module.** One file, 11 entries; abstracting prematurely
   would just be churn.
3. **Encoder primitives live in `src/encoder.zig` (still one file).** The
   `bitstream.zig` / `huffman.zig` / `match.zig` / `blocks.zig` split
   from DESIGN.md is deferred — no second consumer yet justifies the
   abstraction. File is ~1950 lines; manageable.
4. **`encodeBlockFromTokens` doesn't share BitWriter across blocks.**
   Each block call creates + returns its own bytes. Will need to change
   when multi-block lands (blocks within one stream share a bit stream).
5. **Stable fingerprint IDs forever.** Per DESIGN.md backwards-compat
   policy. Don't reuse IDs even if a fingerprint is retired.
6. **Detector returns first match in registry order on byte-equivalence.**
   When configs produce identical bytes (HUFFMAN_ONLY-STORED ≡ L0, L1 ≡
   L6 ≡ L9 on simple inputs), the registry's iteration order decides.
   Eventually we'll order by prior probability (most common configs
   first) but for now it's registration order.
