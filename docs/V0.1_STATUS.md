"generalize enough DEFLATE behavior to recover byte-identical ZIP-family
streams for blar, using difz as the residual-patch fallback."

## Why This Matters To blar

`../blar` expands containers before recompressing their payloads with stronger
compression. ZIP-based formats are the largest immediate target: Office Open
XML, EPUB, JAR, APK, ODT, plain ZIP, and similar formats.

For those files, the archive-time path should:

1. Extract each embedded raw DEFLATE stream.
2. Inflate it to raw bytes.
3. Identify the encoder fingerprint/config that best reproduces the original
   stream.
4. Store the raw bytes under blar's stronger compression, plus the compact
   fingerprint/config.
5. If reproduction is not byte-exact, store a small `../difz` residual patch.

The extract-time path should:

1. Decode blar's stored raw bytes.
2. Recompress with the stored fingerprint/config.
3. Apply any difz residual patch.
4. Rebuild the outer container byte-identically.

That makes this repo less a "fingerprint lookup table" and more a configurable
DEFLATE reproduction engine with attribution as a required API.

## Registry

There are 28 registered fingerprints in `src/lib.zig`.

| ID | Family / behavior |
|---:|---|
| 1 | zlib Z_NO_COMPRESSION / level 0 stored raw DEFLATE |
| 2 | zlib Z_HUFFMAN_ONLY, any level, 3-way block dispatch |
| 3 | zlib level 1 DEFAULT_STRATEGY |
| 4 | zlib level 6 DEFAULT_STRATEGY |
| 5 | zlib level 9 DEFAULT_STRATEGY |
| 6-11 | zlib levels 2, 3, 4, 5, 7, 8 DEFAULT_STRATEGY |
| 12-20 | zlib levels 1-9 Z_FIXED |
| 21 | zlib Z_RLE, collapsed across levels 1-9 |
| 22-27 | zlib levels 4-9 Z_FILTERED |
| 28 | zlib level=1 DEFAULT_STRATEGY data blocks + `SYNC_FLUSH` + empty finish block |

Known collapses:

- Level 0 ignores strategy for raw stored output.
- HUFFMAN_ONLY ignores level for the DEFLATE body.
- RLE ignores level for the currently modeled behavior.
- FILTERED at levels 1-3 follows the deflate_fast path and collapses to
  default level 1-3 output.
- Several default levels produce byte-equivalent output for simple inputs; the
  identifier reports the first matching registry entry.

## Implementation Shape

Current modules:

- `src/bitstream.zig`: LSB-first bit writer and fixed-Huffman emit helpers.
- `src/huffman.zig`: zlib-compatible Huffman tree construction, canonical code
  generation, and code-length RLE.
- `src/match.zig`: zlib-style LZ77 tokenizers for fast, slow/lazy, filtered,
  and RLE strategies.
- `src/blocks.zig`: block cost calculation, stored/fixed/dynamic emitters, and
  multi-block dispatch, including explicit memLevel chunk sizing.
- `src/encoder.zig`: public fingerprint encoder functions plus
  producer-agnostic `DeflateReproductionConfig` for explicit DEFLATE
  reproduction settings such as LZ77 params, memLevel, per-offset sync-flush
  events, finish mode, and tokenization mode.
- `src/lib.zig`: registry, identify/encode APIs, and C FFI exports including
  `dfp_encode_configured` for explicit config-driven compression.
- `src/inspect.zig`: pure DEFLATE block-boundary and token-trace inspector
  covering STORED, fixed-Huffman, and dynamic-Huffman streams for the Excel
  boundary and LZ77-decision probes; also derives observed flush schedules
  from target DEFLATE streams without producer-specific heuristics.
- `src/ooxml.zig`: small OOXML `docProps/app.xml` metadata parser for
  producer/version clustering.
- `tools/zip_corpus_probe.zig`: ZIP-family raw-DEFLATE corpus probe.

The code still uses an inline registry rather than a separate registry data
format. That is acceptable for the current 28-entry research stage, but a
versioned append-only registry remains a v0.1/v0.2 hardening item.

## Corpus Strategy

The work product is byte-exact fingerprint/config reproduction, but the only
way to get there is a large labeled stream corpus:

- Generate known outputs from development-only encoder oracles: zlib versions,
  libdeflate, 7-Zip, miniz, Go flate, .NET DeflateStream, Java `java.util.zip`,
  Apple/CoreFoundation, Info-ZIP/PKZIP/gzip where available.
- Harvest in-the-wild streams from ZIP-container formats, Office/iWork, EPUB,
  PDF FlateDecode, PNG IDAT, gzip, APK/JAR/WHL/XPI/VSIX, OpenDocument, CBZ,
  and other formats with embedded RFC 1951 streams.
- For each stream, store raw bytes, compressed bytes, observed block/flush/token
  summaries, container metadata, and any producer/version metadata.
- Promote only byte-exact reproductions into stable fingerprints/configs; keep
  near-matches as evidence for later reverse-engineering rather than treating
  difz as a replacement for the fingerprinting work.

## Recent Correctness Fix

`src/match.zig` has a zlib `MAX_DIST` fix committed in `zzvvlnuv`:

- zlib uses `MAX_DIST = window_size - MIN_LOOKAHEAD`.
- With default values, that is `32768 - 262 = 32506`, not `32768`.
- Accepting matches with distance 32507-32768 caused token-stream divergence on
  inputs larger than 32 KiB.
- The fix adds `maxDist(params)` and applies it in fast, slow, and chain-walk
  paths.

This is tested by the existing suite and was manually verified against a
46 KiB info-zip case before this checkpoint.

## Active Investigation

Excel `.xlsx` `xl/worksheets/sheet2.xml`:

- Raw size: 279,493 bytes.
- Excel compressed size: 52,876 bytes.
- Registered v0.1 flush/finish wrapper size: 53,419 bytes.
- Small sibling entries in the same archive match zlib L1 + OPC flush/finish.

Open hypotheses:

- Excel changes level or memLevel for large entries.
- Excel uses a different block-boundary heuristic than zlib's default
  16,383-symbol pending-buffer split.
- Excel uses a non-zlib encoder for large worksheet XML.
- The large-entry encoder is a custom point between zlib L1 and L6 behavior.

Peter flagged an important scope concern on 2026-05-25: different Excel
versions may use different zlib versions, deflate implementations, parameter
sets, or streaming flush policies. Treat Office/OOXML as a producer-family
cluster, not one monolithic "Excel fingerprint." Stable fingerprint IDs should
represent byte-reproduction behavior; producer/version labels from
`docProps/app.xml`, ZIP version/subtype fields, platform metadata, and file
timestamps are secondary attribution evidence that should be recorded during
corpus probes.

Initial implementation response:

- `zip_corpus_probe --verbose` now reports `Application` and `AppVersion` from
  OOXML `docProps/app.xml` when present.
- Verbose ZIP-probe misses now include compact DEFLATE block-shape summaries
  (`dynamic:8191 stored:0 ...`) so producer clusters can be compared without
  re-running the full bit inspector manually.
- Local examples already show distinct producer clusters:
  Microsoft Excel `16.0300`, Microsoft Excel `14.0300`, and
  LibreOffice `6.1.0.3`.

Safety fix from the same probe loop:

- Large CPI worksheet streams exposed a production bug where chunked token-only
  block helpers could start a chunk with a match whose distance reached into a
  prior chunk. Per-chunk `reconstructFromTokens()` underflowed in that case.
- Token-only multi-block helpers now reconstruct the full raw stream once and
  delegate to raw-slice-aware helpers for per-chunk STORED fallback decisions.
- A regression test pins the cross-chunk match case; the CPI `.xlsx` verbose
  probe now completes instead of crashing.
